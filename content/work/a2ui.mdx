<Section n="01" title="Context & Business Problem" headline="A chat window that can only print text cannot run enterprise work">

### The enterprise landscape

In an enterprise, AI agents do real work in real systems: HR, payroll, tickets, approvals. In CAMS, people talk to these agents in a chat. In my designs, a People Analytics Agent builds workforce and PTO analytics from HRMS and Payroll data, and a Leave Policy Agent answers leave questions and can file or withdraw requests. The conversation is the front door to all of it.

That makes the conversation the most important surface in the product, and today most agents can only use one tool on it: text.

### The core problem

Text works for a quick answer. It breaks down the moment an agent needs to do something with a person.

- The agent needs a missing detail, so it asks in a paragraph, and the person answers by typing and hoping it is understood.
- The agent makes judgement calls, such as which currency to report in, and buries them in prose where nobody reviews them.
- The agent has a plan, but describes it in sentences instead of showing the steps.
- The agent wants to act, such as emailing a report or withdrawing a leave request, and the permission is one polite sentence with no sign of the consequences.
- The result is a wall of text with a table pasted into it.
- The task takes minutes and the screen shows nothing.

| What people experience | What it costs the business |
|---|---|
| Questions buried in paragraphs, answered by free typing | Misread answers, retries and slow tasks |
| Judgement calls made silently | Wrong assumptions that surface late, after the work is done |
| Permission asked in a sentence | Actions taken without clear consent, and no record of what was agreed |
| Results as pasted text | Hard to scan, hard to trust, hard to act on |
| Silence while the agent works | People abandon the task or ask again |

### The idea: let the agent describe the interface

A2UI is an open-source protocol, created by Google with community contributions, for agent-driven user interfaces. It exists to answer one question: how can an AI agent safely send a rich interface across a trust boundary?

Instead of text-only replies or risky generated code, the agent sends declarative descriptions of components, and the client renders them with its own native components. The agent can only use components from a pre-approved catalogue, so it cannot inject arbitrary UI. The format is flat, streaming JSON designed for language models to generate, and the same message can render on different platforms and frameworks.

<A2UIFlow />

The loop is the same each time: the person sends a message, the agent generates A2UI messages describing the interface, they stream to the client, the client validates and renders them from its catalogue, the person interacts, and the action goes back to the agent.

I then analysed Covasant's Figma design system to see which existing components could be offered to an agent. That analysis produced catalogue schemas and a theming file for matched components, such as the data table, the error message and the text input, with a few token values flagged for manual checking.

### Mapping the conversation

The most useful thing I did was list the moments in an agent conversation that text handles badly, and decide what should replace the text at each one.

| Moment | What goes wrong with text | Component |
|---|---|---|
| The agent needs a missing detail | Questions buried in a paragraph, answered by typing | Question: single or multiple choice, with Other, review and an answered summary |
| The agent faces judgement calls | Assumptions made silently | Decisions: recommended options pre-selected, for review |
| The agent proposes work | A plan described in sentences | Plan: steps, duration, read-only or changing, data sources, and Begin, Modify or Don't start |
| The agent wants to act | Permission buried in one sentence | Permission: what will happen, to which system, who is affected, whether it can be undone |
| The agent needs structured input | Slow back and forth | Form: fields, file upload, searchable dropdown, date and time, validation |
| The agent shows results | Walls of text and pasted tables | KPI cards, table, charts, list, code snippet |
| The agent is working | Silence | Loading and thinking states, then an execution summary |
| Something goes wrong, or there is nothing to show | Raw errors | Error, success, info and empty states |

### What shaped the design

1. **An answered component should become part of the record.** Once a question or a decision is answered it collapses to a single summary line, such as "Answered 2 questions", marked as used by the agent, so the conversation stays readable and auditable.
2. **Permission must show consequences, not just ask.** The question alone is not enough for an irreversible action. The person needs to see what will change, in which system, who is affected, and whether it can be undone.
3. **A plan is a contract.** If the person changes it, the change must be visible. A revised plan shows which steps changed and replaces the earlier version.

### How I defined the behaviour schema

Every component in the catalogue has a contract with four parts.

1. **Purpose and data.** What the agent provides, with the fewest required values, each described in plain language so an agent can use it correctly.
2. **States.** The default, loading, empty, error and success states, plus the states that only matter for interactive components: pending, answered and superseded, and destructive for risky actions.
3. **Actions.** What the person can do, and exactly what is sent back to the agent when they do it.
4. **Adaptation.** How the component changes across scenarios and across surfaces, including where the agent is called from. Inside CAMS the agent uses the full custom catalogue. From outside, it uses basic primitives only.

<SubSection n="01" title="Ask: structured questions instead of paragraphs">

**The problem it solves:** the agent needs information, and typing free text invites mistakes.

**What I designed:** a Question component that walks through one question at a time. A row of small chips shows progress through the questions. Options carry a short description, and an Other option opens a text field. A person can skip, go back, or move on, and an invalid answer is flagged before it goes to the agent. Once answered, the whole thing collapses to a single line the agent has used.

<SubSection n="03" title="Plan and run: show the work before and after">

**The problem it solves:** people cannot see what the agent is about to do, or what it did.

**What I designed:** a Plan component that shows the steps, the estimated time, whether the plan is read-only, and the data sources, with Begin, Modify plan and Don't start. ### Text only, and with components

This comparison shows what the design is built to change. These are design intentions, not measured results.

| Dimension | Text only | With the catalogue |
|---|---|---|
| Collecting a missing detail | A paragraph answered by typing | A question with options, validation and a recorded answer |
| Judgement calls | Made silently | Listed with recommendations, for review |
| Taking an action | Permission asked in a sentence | Consequences shown, and the decision recorded |
| Long tasks | Silence | A plan, visible progress and an execution summary |
| Showing results | Pasted text | KPI cards, tables and charts |
| Something goes wrong | A raw message | A designed error state with next steps |

### What I would measure

How often agent responses use a component instead of text; how many questions are answered without a retry; time from a request to an approved action; and how many unintended actions the permission step prevents.

### Reflections and learnings

The hardest question was never what a component looks like. It was what it does when something goes wrong: the answer is invalid, the person changes their mind, the conversation moves on, the request is stale. Designing those moments is what turns a nice component into something an enterprise can rely on.

The other lesson is about trust. An agent that can generate any interface is risky. An agent that can only choose from a catalogue you designed is predictable. The catalogue is where design and safety meet.
