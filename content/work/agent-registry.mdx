<Section n="01" title="Context & Business Problem" headline="Frontline retail and logistics AI requires strict multi-tenant governance">

### The operational reality of enterprise AI

As part of **Zebra Companion (ZAC)**—Zebra Technologies' GenAI platform for frontline workers across retail, warehouse, and field logistics—AI agents perform high-consequence tasks: stock lookup, sales recommendations, workforce scheduling, and picking coordination.

Unlike standalone chatbots, frontline agents depend on complex backend systems: ERPs, warehouse management systems (WMS), inventory databases, and real-time messaging buses. In an enterprise ecosystem, multiple clients (tenants) often run the same underlying agent blueprints (e.g., Sales Agent, Knowledge Agent, Picking Assistant), but require completely different configurations, prompts, API credentials, and runtime parameters.

### Why ad-hoc agent deployment failed

Prior to the Agent Registry, deploying and updating an agent for a new tenant was an error-prone, fragmented process spread across disconnected tools:

- **Configuration drift:** Engineering teams manually edited Helm values files and JSON manifests. A typo in an environment variable could take down a retail store's inventory lookup.
- **Secret exposure risk:** API keys and database credentials were frequently copied into git repositories or shared via internal chats during onboarding windows.
- **Missing promotion rigor:** There was no structured boundary between development experiments and production workloads. A prompt update tested in a staging sandbox was manually committed directly into production clusters without formal audit trails.
- **Unclear ownership between teams:** Forward-deployed engineers (FDEs) knew the client's business logic, Tenant Admins owned policy and brand compliance, and Cloud Ops owned cluster stability. They lacked a common operational surface.

The brief was to design a unified, web-based Agent Registry that serves as the **single source of truth** for agent blueprints, runtime configurations, tenant mappings, and gated GitOps promotions.

</Section>

### Designing for a Single-Pod, Multi-Tenant Runtime

A fundamental architectural constraint shaped the user experience: **tenants sharing an environment run on a single pod** to minimize cluster resource consumption. A single container instance of the Sales Agent serves multiple retail tenants simultaneously. Tenant isolation is achieved via runtime context injection from the API Gateway based on `tenant_id`.

This architectural principle demanded an absolute visual and conceptual separation in the UI between **behavioral configuration** and **contextual secrets**.

<Figure

  caption="Architecture: Clean separation between behavioral agent_config (ConfigMaps) and contextual env_config (GCP Secret Manager) running inside a shared multi-tenant pod."

### Two distinct configuration classes

| Dimension | `agent_config` (Behavioral) | `env_config` (Contextual / Secrets) |
|---|---|---|
| **What it contains** | System prompts, model temperature, skill parameters, feature flags | API keys, database credentials, third-party auth tokens, webhook URLs |
| **Storage layer** | Versioned Config Records in the Registry database | GCP Secret Manager (GSM); portal persists only secret references |
| **Delivery to pod** | Stamped into Kubernetes ConfigMaps (`cm-{tenant}-{agent}-{hash8}`) | Volume-mounted JSON from ExternalSecrets (`sm-{tenant}-{agent}-{hash8}`) |
| **Visibility in UI** | Full JSON and structured form editor with side-by-side diff | Masked secret fields with zero plain-text values stored in portal logs |

### 1. Module 1: Agent Definition (Agent Library)
Stores agent blueprints: identity, input/output modes, capability tags (streaming, push notifications), dependency graphs, and Helm chart links. Each agent progresses through explicit lifecycle states: `Draft` $\rightarrow$ `Active` $\rightarrow$ `Inuse` (when referenced by an active deployment).

### 2. Module 2: Configuration Management
Defines JSON schemas for agent parameters. Platform administrators maintain reusable **Config Templates** (draft-2020-12 standard), while operators instantiate versioned **Config Records** targeted to specific tenants and environments.

### 3. Module 3: Deployment Plans
Visual directed graphs created on a canvas for complex, standalone deployments. Operators connect Agent nodes to Environments, Tenants, Config Records, and Execution Specifications (replicas and ports).

<Section n="04" title="Helm-Driven Onboarding" headline="Eliminating manual configuration with one-click metadata extraction">

In early iterations, registering a new agent required filling out 18 form fields across four tabs, manually uploading JSON schema definitions, and copying chart versions. It took over 20 minutes per agent and suffered an initial validation failure rate exceeding 40%.

### The Solution: Helm-Driven Auto-Fill

I collaborated with platform engineering to implement a manifest-driven onboarding pattern. Developers publish their agent's Helm chart to the platform's ChartMuseum repository with standard annotations pointing to a `registry-metadata.json` bundle.

<Figure
  src="/work/agent-registry/screens/figma/02-define-agent-helm.webp"
  size="wide"
  zoom
  alt="Define Agent screen showing Deployment Source dropdown and the Fetch and Auto-fill action"
  caption="Helm-Driven Registration: Selecting the chart from ChartMuseum and clicking 'Fetch & Auto-fill' automatically populates schemas, identity, and A2A cards."
/>

### How it works in the interface:
1. **Source Selection:** The operator selects the registered chart from the dropdown (filtered automatically by the `agent-registry` keyword).
2. **Fetch & Auto-fill:** A single click calls the registry backend to inspect the chart package, auto-populating Agent Name, Description, `agent_config` schema, `env_config` schema, and Agent-to-Agent (A2A) protocol declarations.
3. **Collision Prevention:** Only one active Multi-Agent Orchestrator (MAO) agent can exist in the platform. If an operator selects an MAO chart when one already exists, the UI surfaces a prominent conflict banner with a direct link to the existing MAO agent, preventing accidental routing splits.

</Section>

<Section n="05" title="Tenant Onboarding" headline="From zero to running agents in a structured, guided journey">

The core operational workflow of the Agent Registry is **Tenant Onboarding**. FDEs onboard enterprise customers by creating a tenant workspace, configuring gateway routing, mapping agents from the library, setting overrides, and deploying to the base environment.

### Step 1: Tenant Creation & Automatic Gateway Mapping
When an operator creates a tenant, the dialog prompts for a lowercase, DNS-safe tenant identifier and description. Immediately following creation, the wizard presents an optional **MAO Configuration** step.

The Multi-Agent Orchestrator (MAO) acts as the intelligent front door for the tenant. The UI automatically creates the MAO gateway mapping as soon as config records exist for each MAO template. While the system allows skipping this step for initial testing, the UI clearly warns that a tenant version cannot be promoted to production without a mapped gateway.

### Step 2: Mapping Agents to the Tenant
From the Tenant Detail page, clicking **Map Agent** opens a dialog listing all published agents in the library. Once selected, the operator enters the **Map Agent Drawer** to configure per-tenant parameters:

- **Version selection:** Defaults to the latest compatible release, flagged with a `Recommended` badge.
- **Agent description override:** Allows customizing the agent's description specifically for this tenant's A2A routing card.
- **Skills configuration:** Operators can enable or disable specific agent skills (e.g., enabling product lookup while disabling order cancellation) and customize trigger prompts.
- **Config record binding:** Operators select or create tenant-specific `agent_config` and `env_config` records in place without leaving the drawer.

<Section n="06" title="The Revision Forking Model" headline="Absolute GitOps auditability through immutable version snapshots">

In enterprise software running under strict compliance, an in-place edit on a live production workload is catastrophic. To ensure complete repeatability and safe rollbacks, I designed the **Revision Forking Model**.

<Figure
  src="/work/agent-registry/diagrams/d03-revision-forking-model"
  themed
  size="wide"
  zoom
  alt="Diagram explaining the immutable revision forking model: draft in-place edits vs locked promoted major version forking"
  caption="The Revision Forking Model: Deployed and promoted versions are strictly locked. Future modifications fork new revision branches with audit logs."
/>

### The State Rules:
1. **Un-deployed Drafts (In-Place Updates):** While a tenant version is in `Draft` or `Ready For Deployment`, operators can edit skills and configs in place.
2. **Post-Deployment Lock:** As soon as **Deploy To DEV** is clicked, the version locks. Any subsequent edit creates a new minor version (e.g., `1.0.0` $\rightarrow$ `1.1.0`).
3. **Post-Promotion Major Fork:** Once a version is promoted to higher environments, it is permanently frozen. Clicking **Edit Mapping** on a promoted version creates an unlocked major release (e.g., `1.0.0` $\rightarrow$ `2.0.0`) with a mandatory changelog modal.

<Section n="07" title="Three-Gate Promotion Relay" headline="Governing the journey from base environment to cluster pull request">

Promoting a tenant's agent suite to client-facing environments is not a silent, background process. It is a structured relay requiring explicit sign-offs.

<Figure
  src="/work/agent-registry/diagrams/d02-three-gate-relay"
  themed
  size="wide"
  zoom
  alt="Diagram showing the Three-Gate Promotion Relay: Gate 1A automatic base deploy, Gate 1B Tenant Admin review, Gate 2 Cloud Ops sign-off, and PR Raised"
  caption="The Three-Gate Relay: Every promotion moves through an automatic check (Gate 1A) and dual human approvals (Gate 1B & Gate 2) before GitOps PR generation."
/>

### The Three Gates in Detail

- **Gate 1A — Base Environment Deploy (Automatic):** Triggered when the FDE clicks **Deploy To DEV**. Because development requires rapid iteration, Gate 1A performs automated schema checks and approves immediately without human review. The base environment is the only environment configured with `auto_merge: true`, deploying directly to the cluster.
- **Gate 1B — Tenant Admin Review (Manual):** Triggered when an FDE clicks **Promote to Pilot-T**. The promotion request enters the `Pending-Approvals (Tenant Admin)` queue. The reviewer inspects agent configurations, reviews prompt changes using **View Specs** (side-by-side diff), and either approves or rejects with a mandatory rationale.
- **Gate 2 — Cloud Ops Review (Manual):** The final operational checkpoint on the `Pending-Approvals (Cloud Ops)` tab. Cloud engineers review the bulk submission table, verify namespace quotas and secret bindings, and click **Approve Tenant**.

<Figure
  src="/work/agent-registry/screens/figma/15-promotion-requests-tenant-admin.webp"
  size="wide"
  zoom
  alt="Promotion Requests view showing the Pending-Approvals (Tenant Admin) tab with expanded tenant card and View Specs button"
  caption="Promotion Requests (Gate 1B): Tenant Admins review pending promotion requests, inspect config specs, and approve or reject with required audit notes."
/>

### Terminal State & Rollback Recovery
Unlike the base environment, non-base environments (Pilot-T, Production) have `auto_merge: false`. When Gate 2 is approved, the system generates the GitOps branch and pull request, moving the tenant version into **`PR Raised`**. A Cloud engineer merges the PR externally, preserving the human barrier before cluster modification.

If a deployment encounters issues in the next environment, the Tenant Detail header surfaces the **Rollback Current Deployment** action. The operator selects a prior stable revision, and the registry automatically generates a clean rollback PR targeting only the agents that experienced changes.

</Section>

<Section n="08" title="Design Decisions & Polish" headline="Engineering ergonomics and safety mechanisms for high-stakes operations">

### Status Banner Taxonomy
The Tenant Detail banner acts as the definitive operational beacon, reflecting real-time state:

- **`Draft`:** Version exists but no agent is complete yet.
- **`Ready For Deployment`:** At least one agent is complete; displays readiness ratio (e.g., `1/1 Ready for deployment`).
- **`Deployment In Progress`:** Background scheduler running; mutating controls safely disabled.
- **`Ready To Promote`:** Every agent is live and MAO is mapped; unlocks the **Promote to** action.
- **`Partially Deployed`:** Explicitly identifies root cause (e.g., `Partially deployed - MAO is not mapped, 1/2 agents failed`).
- **`PR Raised`:** Terminal non-base state awaiting external GitOps merge.
- **`Promoted`:** Version locked; displays `Use edit version to make an editable copy`.
